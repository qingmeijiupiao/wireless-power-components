# espnow_link

通用 ESP-NOW 链路组件。负责帧编解码、可靠单播、ACK、重传、去重、运行期 peer、配对持久化和射频生命周期。产品消息、设备角色的含义、急停策略和黑匣子记录由产品层处理。组件日志统一使用 `ESP_LOGx`，不依赖 diagnostic_log 或 blackbox。

## 架构

- 链路域：单个 Link 任务（优先级 4、栈 4096）串行处理 `rx_queue(16)` / `tx_queue(16)` / `mac_queue(8)` / `ack_queue(8)`，同一时刻只保留一个在途业务帧（重传/ACK 由该任务推进）。
- 配对域：独立配对任务（优先级 3、栈 4096）处理响应窗口、逐信道发现、信道恢复与 peer NVS 写入；与链路域通过递归生命周期锁和射频事件串行化。
- 业务 `MessageHandler` / `SendCallback` 均在 Link 任务上下文执行，必须快速返回。

## 生命周期与线程约定

- NVS 初始化后调用 `init()`；组件订阅 WiFiManager 射频事件，随 WiFi 启停初始化/释放 ESP-NOW 驱动。射频恢复时从已保存记录恢复 peer。
- `send()` 仅在 `is_active()` 时入队，数据复制到固定队列。`ESP_OK` 表示入队成功，最终结果由回调交付。
- 所有消息处理和发送回调在 Link 任务执行，必须快速返回，不允许同步等待 Link 自身。配对处理放在独立任务。
- 内部递归生命周期锁串行化驱动、peer、NVS 和任务状态；ISR 不获取该锁。`init/deinit` 须由应用串行调用；禁止在 Link 回调调用 `deinit()`。
- 射频停止取消旧请求，清除旧驱动完成事件、接收和 ACK 队列；发送取消回调仍由 Link 任务交付。恢复射频不会复活旧请求。

## 发送取消

`cancel_transmissions()` / `cancel_transmissions_from_isr()` 增加发送代际。此前的所有 `send()` 请求（包括配对帧）停止后续发送/重传，并返回 `SendResult::CANCELLED`；之后提交的新请求不受影响。

ISR 版本仅更新 DRAM 计数，不操作队列、驱动或日志。取消不撤回已提交给射频驱动的帧，不取消协议 ACK，不删除 peer/NVS。旧帧完成前保留驱动占用，防止迟到 MAC 回调被误认为新请求结果；新代际请求仍可能暂时遇到队列满。

## 配对接口

`configure_pairing(PairingConfig)` 仅空闲时调用：

| 字段 | 含义 |
| --- | --- |
| local_role | 0..31 的不透明应用角色编号，0 为未知 |
| accepted_roles | 允许的角色位图，0 表示不筛选 |
| peer_limit | 保存上限 1..3 |
| replace_existing | 只允许 limit=1，确认新绑定后原子替换 |
| allow_legacy | 默认 true，允许原有协议设备 |
| scan_timeout_ms | 主动扫描总窗口，默认 15 秒，范围 1..60 秒 |

单绑定配置会将历史多绑定迁移为保留第一条记录；迁移写入失败返回错误。组件不解释 BUTTON/METER 等名称；这些规则位于产品协议组件。

`enter_pairing_mode()` 开启响应窗口，`start_pairing()` 主动扫描，`leave_pairing_mode()` 取消主动/响应配对及信道恢复。普通任务调用退出会等待清理，Link 回调内调用仅提交取消。退出配对不会全局取消应用发送，已入队的旧握手帧通过事务编号和 nonce 隔离。

`get_pairing_result()` 返回最近终态快照。serial=0 表示无结果，serial 改变代表新结果；包含 peer、channel、error、initiator、legacy。它是最新快照，不是事件队列。`is_pairing()` 表示流程仍在运行，与“存在已保存绑定”不同。

## 配对时序与失败恢复

1. 优先尝试原绑定信道，再按国家允许信道扫描；每信道两次发现，每次等待 150ms，整体最多默认 15 秒。
2. 收集当前信道的响应及角色能力；多个兼容候选时返回 `ESP_ERR_INVALID_RESPONSE`，避免任意选中。不同信道的候选不能保证全部发现，操作时仍应只开启一个目标的配对窗口。
3. 发送请求并交换 LMK；同 MAC 重配优先复用原 LMK。响应端单事务 2 秒超时，失败恢复原 peer，并继续监听剩余窗口。
4. 发起端发送加密确认。新版响应端检查来源和 nonce，先写 NVS，再发送明确的持久化结果；发起端收到成功结果后才保存/替换自己的绑定。
5. 结果丢失时发起端可查询；响应端在 RAM 缓存最近完成事务。写入失败、超时或取消保留发起端原绑定。新目标成功后才删除发起端旧目标。

响应端结果未获得 ACK 时报告超时，但已提交的本机记录不回滚，以免对端已经完成后被单方面删除。协议未提供跨重启持久化事务日志；在确认阶段断电、任一端 NVS 写失败时可能短暂形成单边记录，需要重新开启配对收敛。更换目标后，旧功率计中的历史开关记录不会远程自动删除，可通过其解绑接口清理。

容量满拒绝新 MAC，同 MAC 重配不增加条数。未知旧设备允许配对时不具备角色筛选保证。

## 兼容与存储

原协议 ID 0x0100..0x0104 和 payload 保持不变；新增能力广播 0x0105、新请求/响应 0x0112/0x0113、持久化结果/查询 0x0115/0x0116。未观察到新能力时按旧协议握手，`legacy=true`；旧协议的 ACK 不能证明对端已经持久化，能力帧丢失也可能回退到此路径。

NVS blob 仍为版本 1，复用原保留字节保存应用角色，不改变记录尺寸、MAC、LMK 或原有校验格式。新固件可读旧记录，角色为 0；旧固件无法应用新角色策略。保存、删除、替换均在 NVS 成功后更新运行期缓存。

`get_saved_peer()` 返回角色元数据；`set_saved_peer_role()` 可用于产品识别旧设备，配对/恢复期间返回 INVALID_STATE。`remove_saved_peer()/clear_saved_peers()` 同样要求空闲。
